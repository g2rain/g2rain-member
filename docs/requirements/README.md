# 需求设计与验收模板

重要需求在编码前应创建 `docs/requirements/<feature-name>.md`。文档描述“要实现什么、明确不做什么以及如何验收”，架构长期取舍另行记录到 ADR。

## 何时必须创建

- 新增公开或受信内部 API。
- 新增会员身份类型、状态或跨服务流程。
- 修改数据库表、唯一键、租户隔离、逻辑删除或数据迁移方式。
- 涉及事务、并发、幂等、权限、敏感信息或兼容性。
- 需求需要多个模块或多个项目协同交付。

小型文案修改、局部无行为变化重构通常不需要独立需求文档，但仍需满足测试和完成定义。

## 模板

```markdown
# 需求名称

## 状态

草案 / 开发中 / 待验证 / 已完成

## 背景与目标

为什么需要、解决谁的什么问题、期望结果。

## 非目标

本次明确不处理的能力，防止实现范围扩张。

## 使用场景

参与方、前置条件、主流程和触发方式。

## 输入与输出

字段语义、必填项、返回结果及示例。

## 业务规则

状态、唯一性、租户、事务、幂等和并发规则。

## 权限与安全边界

调用者、认证方式、数据范围、敏感字段和日志限制。

## 数据模型变化

表、字段、索引、迁移、回滚和历史数据处理。

## API 与兼容性

新增或变化的契约、错误码、调用方及兼容策略。

## 异常场景

失败条件、业务错误、重试和告警方式。

## 验收条件

- [ ] 可被测试或观察的明确结果。

## 测试场景

正常、边界、失败、权限、租户、并发和回归场景。

## 发布与回滚

配置、数据、部署顺序、灰度和回滚要求。

## 文档更新范围

需要同步的 README、架构、开发、运维或 ADR 文档。
```

## 编写要求

- 验收条件必须可验证，避免“功能正常”“体验良好”等模糊表述。
- 非目标必须明确，AI Coding 不得自行补充未授权的跨项目能力。
- 未确定事项标注为待决策，不把猜测写成既定架构。
- 实现完成后更新状态，并确保代码、测试与文档一致。
