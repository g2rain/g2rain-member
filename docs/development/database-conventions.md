# 数据库与数据模型规范

## 基础约定

- 使用 MySQL 8.0.13+，会员数据库为 `g2rain_member`。本地、CI、测试和生产环境均不得低于该版本。
- 表和字段使用 snake_case，主键使用平台 `IdGenerator` 生成的 `BIGINT`。
- 租户数据必须包含 `organ_id`，并在查询、唯一键和业务校验中保持一致。
- 时间、版本和逻辑删除字段沿用 `create_time`、`update_time`、`version`、`delete_flag`。
- 字符串比较遵循当前 `utf8mb4_0900_as_cs` 大小写敏感排序规则。

## 会员与身份约束

- `member_no` 在租户内唯一，不包含手机号、机构、日期等业务含义。
- 外部身份由 `organ_id + identity_type + identity_value` 唯一确定。
- 同一租户内，一个会员同一身份类型最多保留一条身份记录。
- 身份唯一键不包含 `delete_flag`：已删除身份继续占位，防止未经核验转移。
- `member.mobile` 是展示冗余字段，手机号身份的权威数据位于 `member_identity`。

## SQL 与索引

- 索引应来自明确查询、唯一性或排序需求，不为“可能使用”盲目添加。
- 唯一约束既是数据完整性边界，也是并发幂等的最后防线。
- 仅有效记录唯一、逻辑删除后允许重新创建时，唯一索引使用函数键 `(IF(delete_flag = 0, 0, NULL))`，不得使用普通 `UNIQUE (..., delete_flag)`。
- 删除后仍需永久占用业务键时，唯一索引不包含 `delete_flag`，并在领域设计中说明原因；`member_identity` 的两个唯一索引属于此类。
- 普通查询索引可以根据查询条件直接包含 `delete_flag`，例如现有的 `idx_organ_status_del`，不需要改为函数索引。
- 查询条件顺序、逻辑删除和租户字段应与索引设计匹配。
- Mapper 显式列出字段，避免表结构变化导致隐式映射扩大。
- `WithoutIsolation` SQL 必须保留明确的租户参数或由调用 Service 完成等价校验。

## 事务与并发

- 会员与身份联合创建必须在同一事务内提交。
- 唯一键冲突后应回滚当前事务，再回查既有身份，不能遗留孤立会员。
- 状态更新和并发写入应使用版本字段或明确的条件更新。
- 数据库异常应转换为稳定业务语义，不能依赖异常文本判断业务状态。

## 结构变更与迁移

- 表结构变化同步更新 `scripts/g2rain-member.sql` 和相关设计文档。
- 当前 SQL 会删除并重建表，只能用于首次初始化或可丢弃开发库，不能作为生产增量迁移脚本。
- 已有数据环境的结构变化必须提供增量迁移、数据校验、执行顺序和回滚方案。
- 修改字段类型、唯一键、排序规则或删除策略时，必须评估历史数据与调用方兼容性。

新增或迁移“仅有效记录唯一”的索引时，至少验证：重复有效记录失败、删除后重建成功、多次删除并重建成功，以及不同租户互不冲突。标准写法见中央 [数据库与租户数据规范 1.0.0](https://github.com/g2rain/g2rain/blob/architecture-v1.0.0/docs/architecture/profiles/java-domain-service/database-policy.md)。

## 数据安全

- 不持久化密码、Token、回调密钥、拉取令牌、验证码或完整客服消息。
- `raw_profile` 仅保存业务必要的白名单字段，并评估保留期限和访问范围。
- 开发配置和生成器不得连接生产数据库或提交生产凭证。
